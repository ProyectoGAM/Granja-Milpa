## 2. Planificación y diseño

Crear `docs/seguridad-gam.md` en la raíz. Dibujar el flujo `navegador o Capacitor → proxy TLS → web Nginx → gateway → Laravel → PostgreSQL/Redis` y marcar las fronteras de Internet, red Docker, unidad productiva y dispositivo. Agregar CI → repositorios y dependencias → imagen → VPS, la comunicación WebSocket de Reverb, las integraciones externas y el almacenamiento de respaldos. Inventariar credenciales de usuarios y servicios, sesiones, datos de clientes, saldos y movimientos, stock, adjuntos, código, imágenes y backups. Registrar dónde viven, quién puede acceder y qué evidencia protege cada activo.

Usar impacto y probabilidad de 1 a 3. Impacto 1 corresponde a un fallo localizado y recuperable, 2 a exposición limitada o interrupción operativa y 3 a acceso a credenciales, exposición entre unidades, alteración financiera o pérdida de datos. Probabilidad 1 requiere acceso privilegiado y condiciones adicionales, 2 requiere acceso regular o una configuración equivocada y 3 corresponde a una superficie expuesta o un flujo frecuente. Multiplicar ambas cifras. Priorizar primero 6–9, después 3–4 y luego 1–2. Registrar responsable, control, prueba, estado y riesgo residual tras verificarlo. Usar esta lista inicial y actualizarla con evidencia durante la implementación. [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) · [OWASP Threat Modeling](https://owasp.org/projects/threat-modeling-project/)

| ID | Amenaza y riesgo inicial | Requisito y evidencia de cierre |
| --- | --- | --- |
| R1 | Un usuario lee o modifica datos de otra unidad. 3 × 2 = 6. | Laravel comprueba rol, dispositivo, sesión y alcance por operación. Probar listas, agregados y acceso por ID con dos unidades, y comprobar que una operación denegada no cambia datos. |
| R2 | Robo, reuso o adivinación de sesión, PIN o código de vinculación. 3 × 2 = 6. | Mantener límites por identidad/dispositivo, revocación, expiración, CSRF y custodia web/nativa. Probar 401, el 429 con `Retry-After` según contrato, la revocación y cookies por HTTPS. |
| R3 | Entrada inválida o repetición modifica saldos, stock o auditoría. 3 × 3 = 9. | Validar en servidor. Conservar UYU exacto a tres decimales, movimientos inmutables, reversiones compensatorias, idempotencia y `409` ante conflicto de versión. Probar 422 sin mutaciones, reintento sin duplicación y reversión con auditoría. |
| R4 | Una dependencia o imagen vulnerable llega a producción. 3 × 2 = 6. | Ejecutar SAST, SCA y escaneo de imágenes con un control antes del release. Registrar SHA, imagen por digest, plataforma, resultado y remediación. |
| R5 | Configuración del borde o de producción expone servicios, sesiones o datos. 3 × 2 = 6. | Verificar TLS, headers, CORS, proxies de confianza, permisos del runtime y redes. Combinar prueba pasiva de HTTP, revisión de Compose y evidencia del borde. |
| R6 | Una instalación compartida, los logs o un respaldo exponen datos o credenciales. 3 × 2 = 6. | Mantener secretos fuera de repos y reportes, almacenamiento nativo seguro y datos locales separados por actor. Revisar revocación, datos visibles en logs, permisos, cifrado y restauración de backups. |

## 3. Suite de seguridad aislada

Crear los siguientes archivos en la raíz. Usar Docker Compose v2.24.4 o posterior y `bash`, `git` y `python3` del host para orquestación y lectura de reportes. Los escáneres corren dentro de Docker. Usar un runner Linux hospedado por GitHub para CI.

| Archivo | Responsabilidad |
| --- | --- |
| `compose.security.yaml` | Servicios de una sola ejecución `semgrep`, `trivy` y `zap`. Configurar la red `dast-front` como red interna del proyecto. |
| `security/compose.target.yaml` | Servicios descartables `web`, `gateway`, `api`, `app-init`, `postgres`, `redis` y `swagger-ui`. Usar `dast-front` y una segunda red interna `dast-back`. |
| `security/run.sh` | Validar el entorno, preparar insumos, llamar al Compose y evaluar el resultado. |
| `security/check-http.php` | Comprobar rutas, respuestas y atributos de cookies desde el contenedor API a través de la web. |
| `security/semgrep/` y `security/zap.yaml` | Reglas SAST y plan pasivo de ZAP, versionados. |
| `security/check-results.py` y `security/exceptions.json` | Validación de reportes, política y excepciones específicas. Iniciar con una lista vacía. |
| `security/README.md` | Comandos, requisitos, alcance, archivos de salida y recuperación. Enlazarlo desde `readme.md` cuidando sus cambios locales. |

Implementar esta interfaz. `all` ejecuta `code`, construye y escanea imágenes, y ejecuta DAST sobre las imágenes de esa corrida. `code` ejecuta SAST y SCA para `backend`, `frontend` o ambos. Usar el mismo script desde local y CI. Resolver las rutas desde la raíz recibida o desde el directorio del script, con independencia del directorio de trabajo.

```bash
bash security/run.sh code
bash security/run.sh code backend
bash security/run.sh code frontend
bash security/run.sh all
```

## 5. SCA e imágenes con Trivy

1. Escanear por separado `GAM-Backend/composer.json` con `composer.lock`, `GAM-Frontend/package.json` con `package-lock.json` y el npm auxiliar del backend. Para este último, en el checkout revisado existe `package.json` pero falta `package-lock.json`: generar y versionar el lock con Node 24 en Docker (`npm install --package-lock-only --ignore-scripts`), revisar el diff y comprobar `npm ci --ignore-scripts` con ese lock. Mantener cada par de archivos en un directorio de insumos separado. Confirmar que los manifests y locks concuerdan. Un lock requerido ausente es error de la suite. [Trivy PHP](https://trivy.dev/docs/latest/guide/coverage/language/php/) · [Trivy Node.js](https://trivy.dev/docs/latest/guide/coverage/language/nodejs/)
2. Por cada par ejecutar `trivy fs --scanners vuln --list-all-pkgs --format json --output <reporte> <directorio>`. Repetir con `--include-dev-deps` y nombre diferenciado. Validar que aparece el lock esperado con su `Type` y paquetes parseados aunque no haya vulnerabilidades. Conservar la política más estricta de `npm audit --omit=dev` en el CI del frontend. Los locks npm cubren los paquetes JS de Capacitor. Registrar que la resolución transitiva nativa de Gradle y Swift queda fuera de este primer control, ya que el checkout carece de locks nativos versionados; documentar los build files y plugins que deben auditarse cuando se incorpore una pipeline de binarios.
3. Construir `Dockerfile --target runtime` de cada submódulo en su snapshot, respetando los argumentos de sus Compose de producción. Generar la lista de imágenes auxiliares con `docker compose … config --images` en cada repositorio y un env sintético. En el estado actual incluye PostgreSQL 18, Redis 8, Swagger UI y Nginx unprivileged del gateway. Descargar cada referencia de esa lista para la plataforma elegida, excluyendo las referencias lógicas `gam-backend:<RELEASE_SHA>` y `gam-frontend:<RELEASE_SHA>`, que corresponden a las dos imágenes construidas. Registrar referencia, SHA o digest según corresponda, ID local y arquitectura. Deduplicar imágenes por ID. Usar estas mismas imágenes auxiliares por digest o ID en el fixture, sin volver a resolver el tag.
4. Exportar cada imagen desde el host con `docker image save -o <temporal.tar> <referencia>`. Pasar el tar de solo lectura a Trivy y ejecutar `trivy image --input <tar> --scanners vuln --list-all-pkgs --format json --output <reporte>`. Validar el inventario del SO y el identificador de imagen. Quitar el tar al terminar su etapa para liberar espacio. El SCA del lock npm sigue siendo obligatorio porque la imagen web contiene los bundles ya compilados. [CLI de Trivy Image](https://trivy.dev/docs/latest/guide/references/configuration/cli/trivy_image/)
5. Actualizar la base de vulnerabilidades una vez por corrida con `trivy image --download-db-only`. Reutilizar esa base con `--skip-db-update` y registrar `UpdatedAt` del metadata. Reintentar una vez con espera ante timeout o rate limit y permitir una fuente oficial alternativa documentada en caso de caída del registro. Exigir una base legible, compatible y con antigüedad máxima de 48 horas. Si la actualización falla, registrar el uso de una caché que cumpla esos requisitos. Evitar caché compartida con escritura entre corridas concurrentes o bloquear la actualización y copiar la base aprobada a un temporal por corrida. [Bases de Trivy](https://trivy.dev/docs/latest/guide/configuration/db/)

## 6. DAST pasivo sobre la web y la API

1. Usar las imágenes `runtime` que Trivy acaba de leer. Configurar `pull_policy: never` para los servicios del fixture y comparar el ID de sus contenedores con el inventario de imágenes antes de escanear. Conectar `web` a ambas redes para alcanzar `gateway:8080`. Conectar `postgres`, `redis`, `app-init`, `api`, `gateway` y `swagger-ui` solo a `dast-back`. Reutilizar los templates Nginx de los snapshots y configurar `API_UPSTREAM=http://gateway:8080`. `swagger-ui` está presente porque el gateway resuelve ese upstream al cargar el template. Los recursos del proyecto nacen vacíos. El fixture solo necesita migrar, sin seed ni credenciales de usuarios. Ejecutar `php artisan migrate --force --no-interaction` en `app-init` tras la salud de PostgreSQL y Redis, luego iniciar FPM, gateway y web. Usar la configuración de producción para debug, cookies y middleware con valores sintéticos de `APP_KEY`, pepper, DB y Redis, `APP_URL=http://web:8080` y `DEMO_DB_RESET_ENABLED=false`. Cubrir Reverb y servicios externos mediante verificaciones de configuración y pruebas específicas fuera de este recorrido HTTP.
2. Esperar salud de FPM y gateway y luego de `/healthz` en la web, con tope global de 180 segundos. Comprobar `/api/v1/health` a través de `web` y exigir JSON con `status=ok`. Un `200` HTML desde la SPA indica un error de proxy o ruta. Detener la etapa. Para resolver `502`, comprobar `app-init`, FPM, templates y DNS interno en ese orden. Ante ausencia del servicio web o del marcador de salud, resolver la causa antes de lanzar ZAP.
3. Ejecutar `docker compose … exec -T api php < security/check-http.php`. Usar cURL de PHP con redirecciones desactivadas, timeout por petición y el origen fijo `http://web:8080`. Ejecutar todos los GET de la tabla. Analizar cada línea `Set-Cookie` por separado e informar únicamente nombre y atributos. Guardar ruta, código, tipo de contenido y resultado de aserciones por solicitud. Un fallo de transporte tras el arranque es error operativo. Una respuesta recibida que incumple el contrato es un hallazgo bloqueante.
4. Configurar `security/zap.yaml` con un único contexto `http://web:8080` y las solicitudes fijas de la tabla. Ejecutar `zap.sh -cmd -autorun /config/zap.yaml`. El plan usa `passiveScan-config` con `scanOnlyInScope: true`, `requestor`, `passiveScan-wait` con `maxDuration: 0` y `report` en ese orden. Usar `responseCode` para cada expectativa. Omitir ZAP si el comprobador confirma un incumplimiento del contrato HTTP de destino y registrar el bloqueo. Si un código no coincide solo en ZAP o el plan reporta advertencias de ejecución, registrar un fallo operativo. Usar un límite externo de tres minutos para toda la ejecución de ZAP. Así, el job `report` se inicia cuando termina el drenaje, y un timeout externo queda como error operativo. Guardar un reporte `traditional-json` que carezca de cuerpos HTTP. Las pruebas Laravel cubren operaciones autenticadas y validaciones con sus propios fixtures. [Requestor](https://www.zaproxy.org/docs/desktop/addons/automation-framework/job-requestor/) · [Espera pasiva](https://www.zaproxy.org/docs/desktop/addons/passive-scanner/job-pscanwait/) · [Reportes ZAP](https://www.zaproxy.org/docs/desktop/addons/report-generation/automation/)

| Solicitud GET | Respuesta esperada | Prueba adicional |
| --- | --- | --- |
| `/` y `/auth` | `200` HTML | SPA servida desde la imagen final, `nosniff` y protección contra iframes. |
| `/api/v1/health` | `200` JSON | Cuerpo `status=ok` y API servida a través del gateway. |
| `/api/v1/me` con `Accept: application/json` | `401` `application/problem+json` | Respuesta sin información identificatoria ni trazas internas. |
| `/sanctum/csrf-cookie` con origen propio | `204` | Verificar atributos en los headers sin guardar valores. La cookie de sesión debe ser `Secure` y `HttpOnly`. La cookie `XSRF-TOKEN` debe seguir siendo legible para el cliente web. |

Mantener la URL fija y la red sin salida. El fixture usa HTTP interno, por lo que el TLS, HSTS y el comportamiento real del navegador con las cookies se validan en el borde según la sección 7. La aparición de una alerta o la ausencia de alertas en estas rutas no determina cobertura de autorización, reglas de negocio o navegación autenticada.

## 7. Controles de aplicación y hardening

1. Revisar las rutas de identidad, clientes/cuenta corriente, reparto, adjuntos y auditoría siguiendo la cadena ruta → Form Request → policy/middleware → acción → consulta. Usar `AuthenticationTest`, `SharedDeviceAuthenticationTest`, `ProductionUnitIsolationTest`, `SessionManagementTest`, `CustomerAccountTest`, `CustomerAccountConcurrencyTest` y `DeliveryEndpointTest` como punto de partida. Relacionar cada control con un método de prueba existente. Si falta un caso de R1, R2 o R3, agregarlo en la suite correspondiente. Probar 401/403/404 conforme a su contrato, 422 y ausencia de mutación para inputs inválidos, CSRF ausente o válido en una petición web, revocación, limitación y propiedad del recurso. Para CSRF confirmar que el middleware esté habilitado en esa prueba, ya que el entorno de testing puede omitirlo. Corregir en la capa responsable y volver a ejecutar el caso y su suite. Preservar el patrón actual de cuentas personales, dispositivos compartidos, permisos, `expected_version`, UYU y auditoría.
2. Probar que el navegador conserva solo cookies de sesión protegidas y que Capacitor usa la capa de almacenamiento seguro para PAT y credencial de dispositivo. Probar cambio de actor y cierre en un dispositivo compartido y confirmar que los datos offline de otro actor queden inaccesibles. Revisar logs y trazas de login, PIN, sesiones y acciones sensibles. Usar pruebas con credenciales sintéticas y comprobar que sus valores no se reflejan en respuestas, logs ni auditorías. Seguir el contrato de PIN como texto de cuatro dígitos.
3. Validar ambos `compose.prod.yaml` con datos sintéticos y afirmar en el modelo renderizado `APP_DEBUG=false`, `SESSION_SECURE_COOKIE=true`, servicios de datos sin puertos publicados, ausencia de Docker socket, ausencia de `privileged`, y los controles `USER`, `read_only`, `cap_drop` y `no-new-privileges` donde ya se aplican. Verificar `DEMO_DB_RESET_ENABLED=false` para producción de cliente. Mantener las reglas existentes del flujo demo donde esté explícitamente habilitado. Comprobar que el Swagger interno quede detrás del gateway y que el borde exponga solo las rutas aprobadas.
4. Revisar la cadena de proxy antes de modificar `trustProxies(at: '*')` en `GAM-Backend/bootstrap/app.php`. Inspeccionar el `edge_nginx` y redes de la instalación aprobada. Comprobar que el primer proxy sobrescriba los headers forwarded de clientes, que gateway y FPM estén aislados y que Laravel vea el esquema y la IP correctos. Si alguna comprobación falla, corregir en el borde y restringir proxies en Laravel a los rangos o saltos comprobados. Verificar rate limiting, generación de URL, cookies y Reverb después del cambio. Registrar orígenes exactos para CORS, Sanctum y Reverb, incluyendo los orígenes de Capacitor autorizados por el contrato. Confirmar que un origen ajeno carezca de autorización CORS.
5. En staging autorizado con el proxy real, verificar redirección HTTP → HTTPS, cadena de certificado válida, web y API saludables por HTTPS, login y logout por cookies, HSTS según el dominio y ausencia de detalles internos en errores.
